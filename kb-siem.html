NOTE 10 / Security operations

SIEM_

Concept Concept study

IN PLAIN ENGLISH

A SIEM collects searchable security data from different systems and applies detection rules. It helps an analyst investigate a sequence of events across the environment.

Why collect logs together?

A firewall can show a blocked connection. A Windows server can show a failed logon. An email system can show message delivery. Opening each device separately is slow, especially across many customers. A Security Information and Event Management platform brings configured sources into a place where you can search and compare them. Microsoft Sentinel is one example.

Follow the data

  1. Generate: a source system records an event.
  2. Collect: an agent, API connector, or log forwarder sends it.
  3. Parse: fields such as timestamp, account, IP, and action become searchable. Some connectors also normalize different vendor formats into common fields.
  4. Detect: a rule evaluates the data, for example many failed logons followed by a success.
  5. Investigate: an analyst examines the alert and related evidence. Several related alerts may be grouped into an incident.

An event records something that happened. An alert flags activity that matched detection logic. An incident is a unit of investigation that can group related alerts and entities. These are not interchangeable.

Work through a simple case

Imagine 30 failed logons against one server, followed by a successful logon from the same source. A detection rule might raise an alert. The analyst asks whether the account normally signs in that way, what kind of logon succeeded, and what happened afterward. The pattern could indicate password guessing, but it could also involve a broken service followed by a legitimate user. The raw events and context support the conclusion.

A rule must define its time window, grouping, exclusions, and threshold. Thirty failures against one user are a different question from thirty failures spread across many users. Tuning is the process of adjusting detection logic to make it useful while preserving visibility.

What a dashboard cannot prove

  • No alert does not prove no attack occurred. Data may be missing, a rule may not cover the behavior, or a threshold may not be reached.
  • A map based on an IP address estimates the address’s location. It does not identify the attacker’s physical location.
  • A colorful dashboard is a view of data. Verify source health, timestamps, and fields before trusting its interpretation.
  • Central collection does not automatically grant response authority. Automated actions need configured permissions and an approved workflow.

Use it during daily review

Check the incident queue and source health. For an investigation, select the correct customer or workspace, define a time range, and search the account, device, or IP. Record relevant results and the query that produced them. Compare endpoint and identity evidence where available. Escalate with a concise timeline, impact, actions already taken, and the next decision needed.

PUT IT INTO WORDS

Check your understanding

How can a SIEM contain logs without producing an alert about those logs?

Show an example answer

Collection and detection are separate. The source may be sending events successfully while no enabled rule matches the behavior, its threshold is not reached, or its query looks in the wrong table or time range. Check the raw events before changing the detection.
