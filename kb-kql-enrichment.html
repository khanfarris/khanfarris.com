IN PLAIN ENGLISH

Kusto Query Language lets you ask questions of tables of data. Each pipe passes the previous result into another step, such as filtering rows or counting events.

Start with a table and a question

A table contains rows and named columns. A security event might have TimeGenerated, Computer, and EventID columns. A query such as “which machines had the most failed logons today?” filters the rows and summarizes what remains. KQL is the query language; Microsoft Sentinel and other services provide places to run it.

SecurityEvent
| where TimeGenerated > ago(24h)
| where EventID == 4625
| summarize FailedLogons = count() by Computer
| order by FailedLogons desc
Line or operatorMeaning
SecurityEventStart with this table. It must exist in the selected query environment.
whereKeep only rows that meet the condition.
ago(24h)The time 24 hours before now.
summarize … by ComputerGroup by computer and calculate a count for each group.
order by … descPut the largest counts first.
project / takeChoose output columns / limit the number of returned rows.

Practice without a connected log source

let Events = datatable(Computer:string, EventID:int)
[
  "PC-01", 4625,
  "PC-01", 4625,
  "PC-02", 4624
];
Events
| where EventID == 4625
| summarize Failures = count() by Computer

In a Kusto-compatible query window, this creates fictional data inside the query. The result is PC-01 with a count of 2. No live customer logs are needed. The semicolon ends the named let expression before the final query.

Add context with a lookup

The study lab matched IP addresses to a separate range-based geolocation dataset. This is enrichment: adding context from another table. An IPv4 range lookup needs a column containing an event’s IP and a column containing the reference CIDR range. Column names are case-sensitive.

let Geo = datatable(Network:string, Region:string)
["192.0.2.0/24", "Example region"];
let Events = datatable(SourceIP:string)
["192.0.2.25"];
Events
| evaluate ipv4_lookup(Geo, SourceIP, Network)

This is a fictional range-label example, not a real geolocation result. The ipv4_lookup plugin is used in supported environments such as Azure Monitor; check support in the query surface you are using. The event supplies SourceIP, while Geo supplies Network.

Debug the error you actually have

  • “Failed to resolve column” means a named column is absent at that query step. Inspect the actual source columns and spelling.
  • No rows can mean the filters exclude everything, the time range is wrong, or data is absent. Begin with a small unfiltered sample.
  • A workbook still using _GetWatchlist() is not fixed by changing a separate query to externaldata. Update the consumer’s own query.
  • A JSON syntax error in a workbook definition occurs before KQL execution. Fix the enclosing document separately.

The lab used an external map template and location dataset. Their outputs are useful context, but an IP-derived map does not locate a person or prove attribution. Keep credentials and signed dataset links out of published queries.

PUT IT INTO WORDS

Check your understanding

Why would ipv4_lookup fail when the reference table has a column called Network but the query uses network?

Show an example answer

KQL column names are case-sensitive. The query must name the actual reference-side range column and the event-side IP column. Inspect the schema and test a small result before troubleshooting the map that consumes it.
