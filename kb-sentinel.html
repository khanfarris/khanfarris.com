Microsoft Sentinel_

Tool guide Lab application

IN PLAIN ENGLISH

Microsoft Sentinel lets you connect security data, query it with KQL, investigate incidents, and build workbooks and detection rules around the connected data.

This guide focuses on the product and the Windows-event collection path used in the study lab. For the general role of this type of platform, read SIEM. Microsoft Sentinel and SentinelOne are separate products.

Find the feature you need

In the Defender portal, Sentinel features sit alongside the unified incident and hunting experience. Older lab material may use the Azure portal. The table below follows Microsoft’s current navigation reference; menus and access can vary with the workspace, role, and enabled services.

Know the pieces in the Windows lab

ComponentIts job in this collection path
Event ViewerShows events recorded on the Windows machine itself. Useful for confirming an event exists before troubleshooting collection.
Azure Monitor Agent (AMA)Collects the configured events from the machine.
Data Collection Rule (DCR)Specifies what to collect and where to send it; the machine must be associated with the rule.
Log Analytics workspaceStores the collected records in tables. The Windows Security Events via AMA connector uses SecurityEvent.
SentinelUses the connected data for queries, detections, incidents, and visualizations.

Run a first query

SecurityEvent
| where TimeGenerated > ago(24h)
| where EventID == 4625
| project TimeGenerated, Computer, Account, IpAddress
| order by TimeGenerated desc
| take 50

This selects up to 50 recent failed-logon records. It requires access to the appropriate workspace and a populated SecurityEvent table. It is a log query, not automatically an alert. Column names and tables in other connectors can differ.

When a query returns nothing

  1. Check the correct machine’s Event Viewer for a known event and timestamp.
  2. Check agent health and the machine’s DCR association.
  3. Confirm the DCR selects the necessary Security events and destination workspace.
  4. Check the table, workspace access, time range, ingestion delay, and query filters.
  5. Test with a small query before rebuilding a workbook or detection rule.

Review an incident

Confirm its status, owner, time range, associated alerts, and affected entities. Inspect the underlying events and record the timeline and response. A workbook is a visualization; an analytics rule defines detection logic. Updating a workbook does not fix an unrelated analytics rule.

Lab troubleshooting lesson

When a workbook expects a watchlist but the data source changes, update the workbook’s own query too. Inaccessible portal navigation and a missing query column are separate problems. Check workspace onboarding and permissions for the first; inspect the data schema for the second.

PUT IT INTO WORDS

Check your understanding

A known failed logon exists in Event Viewer but is absent from Sentinel. What would you check next?

Show an example answer

Check AMA health, the machine’s DCR association, the selected event collection, and the destination workspace. Then verify SecurityEvent, your access, the time range, and ingestion delay. The local event confirms generation; it does not prove collection succeeded.
