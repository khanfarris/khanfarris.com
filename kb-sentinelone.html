SentinelOne_

Tool guide Tool study

IN PLAIN ENGLISH

SentinelOne’s console lets you inspect protected devices, investigate detections through Storyline, and check or perform response actions on the affected endpoint.

This is a console study guide. For the general security categories, read EDR, MDR, and XDR. SentinelOne is a different product from Microsoft Sentinel. Product screens, labels, available actions, and access depend on the console version, operating system, license, and assigned role.

Find the right place

Area or featureUse it to
Account / Site / Group scopeConfirm which customer and device group you are viewing before investigating or acting.
Endpoints / SentinelsFind a device and inspect its identity, operating system, agent health, last contact, policy, and connectivity.
Alerts / ThreatsReview detections, timestamps, severity, status, and any actions already attempted.
Storyline / ExploreInspect linked activity and the process tree: what launched what, and what each process did.
Deep VisibilitySearch available historical endpoint activity, such as a filename, hash, process, or network destination.
Policy and response controlsReview configured behavior and permitted actions. Verify the selected scope before changing anything.

Work through a detection

  1. Confirm the customer and endpoint. Record the detection ID, time, username, and current status.
  2. Open the detection details. Read the reason it fired and the action results. A failed or pending action needs different follow-up from a completed one.
  3. Inspect Storyline. A process is a running program; its parent is the program that launched it. Read the command line, file path, signature information, and related network activity.
  4. Compare the activity with approved software and change records. PowerShell can be legitimate administration; the command, origin, and behavior matter.
  5. Search related indicators across the authorized customer scope if needed. Determine whether the same file or activity appears elsewhere.
  6. Record your finding and the response result, and coordinate with the MDR provider or incident owner before duplicating actions.

Know what the response buttons affect

ActionWhat to confirm
Kill processStops the selected malicious process or supported threat-related processes. Does not by itself prove all persistence was removed.
Quarantine fileMakes the identified file unavailable for normal use. Check the action result and exactly which artifact was affected.
Network isolation / disconnectRestricts the endpoint’s network communication, with management exceptions depending on the product. Can disrupt user work and remote support.
Remediate / RollbackSupported cleanup or recovery actions. Availability and recovery coverage vary; rollback is not a substitute for backups.
Resolve / mark benignUpdates the investigation classification or workflow. Closing an alert is not proof that the underlying device was cleaned.

Practice reading a Storyline

Fictional activity
09:41  outlook.exe opens an attachment
09:42  attachment starts powershell.exe
09:42  powershell.exe downloads a new executable
09:43  SentinelOne reports a detection; process termination succeeds

The useful question is whether the behavior matches a legitimate workflow, and what happened before termination. Check the downloaded file, network destination, additional child processes, user context, and any later activity. “The process was killed” answers one part of the investigation, not whether account credentials or other devices were affected.

Useful ticket evidence

Capture the detection ID, endpoint and customer, relevant Storyline details, indicators, timestamps with time zone, completed and failed actions, and the current owner. If the agent is offline, record its last contact and verify the device’s actual state before assuming a queued action has happened.

PUT IT INTO WORDS

Check your understanding

A threat says “resolved,” but the endpoint has been offline since before isolation was requested. What do you verify?

Show an example answer

Verify the isolation action’s result and the device’s current connectivity, not just the alert’s workflow status. Check last contact and pending or failed actions. Coordinate the next containment step with the incident owner and document the uncertainty.
