NOTE 11 / Security operations

Email authentication_

Concept Scenario study

IN PLAIN ENGLISH

SPF, DKIM, and DMARC help check whether a message is authorized to use a domain. They do not prove that the sender is honest or that the request is safe.

Start with the visible sender

An email contains several sender-related fields. The display name is the friendly label, such as “Finance Director.” The From address is what the mail client displays. The envelope sender is used during delivery and can differ from that visible From address. Authentication checks these identities in specific ways; a convincing display name proves very little.

What each check means

CheckPlain-English questionLimit
SPF — Sender Policy FrameworkIs this sending server authorized in DNS to send for the envelope-sender domain?An SPF pass alone does not authenticate the visible From domain. Forwarding can complicate SPF.
DKIM — DomainKeys Identified MailDoes a valid signature from the signing domain verify the signed parts of this message?It checks signed content and domain responsibility, not the truth of the message or every possible header.
DMARC — Domain-based Message Authentication, Reporting, and ConformanceDid SPF or DKIM pass with a domain that aligns with the visible From domain?A passing message can still be fraudulent. A failing result needs delivery-path context.

DMARC needs at least one aligned passing method, not both. Alignment means the authenticated domain matches the visible From domain according to the configured strict or relaxed rules. Relaxed alignment can allow related subdomains of the same organizational domain.

Compare three messages

Fictional caseWhat the checks can tell you
Forged From: finance@company.example, sent through an unauthorized systemDMARC can fail because neither SPF nor DKIM passes with alignment to company.example.
From: finance@company-payments.example, a lookalike domain owned by an attackerSPF, DKIM, and DMARC can all pass for the attacker’s own domain. The domain still is not company.example.
A real employee mailbox has been compromisedMessages sent through the legitimate service can authenticate successfully while carrying fraudulent instructions.

Read it during phishing review

Use your email security platform or the original message headers to inspect the receiving system’s authentication results. Compare the actual From address, Reply-To, envelope sender, DKIM signing domain, and links with the organization the sender claims to represent. A raw authentication-looking header supplied by an untrusted sender is not automatically trustworthy; use the results from your trusted receiving system.

Then inspect the request itself. Was a bank account changed? Is the message pressuring the user to bypass a normal process? Did the recipient click, download, enter credentials, or approve MFA? Search for other recipients and related activity through the available email tools.

Understand the policy

A domain’s DMARC policy can request monitoring only (p=none), quarantine, or rejection of failing mail. Receiver handling also depends on the receiving system’s policies. Publishing a monitoring policy is not the same as enforcing rejection.

PUT IT INTO WORDS

Check your understanding

Why can a lookalike domain pass DMARC?

Show an example answer

The attacker can configure valid SPF and DKIM for the domain they own, aligned with that domain’s From address. DMARC checks domain authorization, not whether the domain is the real company or whether the payment request is legitimate.
