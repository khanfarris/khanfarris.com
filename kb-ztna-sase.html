NOTE 10 / Identity & access

ZTNA / SASE_

Concept Concept study

IN PLAIN ENGLISH

ZTNA checks who is requesting access and the conditions of that request before allowing a path to a resource. SASE combines secure access with wider networking and security services.

Start with a remote employee

An employee at home needs a company finance application. That application might be on a private office server, so an ordinary internet connection is not enough. Zero Trust Network Access provides an approved path based on identity, the requested resource, and configured context such as device status.

A resource can be an internal web application or another supported private service. The employee may use a local client or a browser, depending on the product and application. They do not necessarily open a virtual Windows desktop. The goal is to grant the required access with the conditions the organization has chosen.

Walk through an access request

  1. The employee signs in using the organization’s identity provider.
  2. The service evaluates the applicable access policy: user or group, resource, and relevant device or risk conditions.
  3. If requirements are met, the system provides the permitted connection to that resource.
  4. The application still checks its own sign-in and permissions. Network access does not automatically grant access to every file.
  5. Access can be reevaluated when supported signals or sessions change. The exact timing and behavior depend on the implementation.

A personal computer is not universally allowed or forbidden by ZTNA. The organization may require a managed device, allow limited browser access, or use another design. Likewise, “always on” describes how a configured client maintains protection; it does not mean every resource is available to every signed-in user.

Where SASE fits

Secure Access Service Edge, commonly pronounced “sassy,” is the broader architecture. It combines networking, such as software-defined wide area networking (SD-WAN), with cloud-delivered security. Common parts include ZTNA, web filtering through a secure web gateway, controls for cloud application use through a CASB, and firewall-as-a-service. A product may deliver a subset; verify the deployed capabilities.

Use it on a support ticket

For “I can sign in but cannot reach the app,” separate identity, policy, network path, and application permissions. A successful MFA challenge confirms one requirement, not every requirement. Check the request’s policy result, device state, DNS, connector or gateway health, and the resource itself. A precise denial reason is more useful than turning off a policy to make the error disappear.

Conditional Access is one part of the picture

A sign-in policy can require MFA or a compliant device for an application. By itself, that policy does not create a network path from a home laptop to a private file server. The access service and the application’s own permissions still matter.

PUT IT INTO WORDS

Check your understanding

Why does successful MFA not guarantee that an employee can open a private file share?

Show an example answer

MFA satisfies an authentication requirement. The device and request must also meet the access policy, the private server must be reachable through an approved path, and the user must have permission on the share and files.
