IN PLAIN ENGLISH

Timus Manager is the web console for administering users, devices, sites, and access policies. Timus Connect is the client application employees use to connect through the configured service.

This is a product cheat sheet. The general access model and the comparison with a VPN or virtual desktop are covered in ZTNA / SASE. Timus does not provide a Windows desktop for the user to log into like a Citrix virtual desktop session.

Recognize the two interfaces

InterfaceWhat happens there
Timus ManagerAdministrators manage the customer’s configuration, users, teams, devices, sites, policies, integrations, and logs.
Timus ConnectAn employee signs in and connects from the endpoint using the configuration assigned to them.
User portalUsers can obtain the client through the available downloads workflow. Administrators also have downloads in Manager.

Find the setting behind the symptom

Manager areaWhat to inspect
Users / TeamsThe correct user record and team membership. Compare with a working user who should have equivalent access.
Devices / Agent ProfilesThe device record and the profile or requirements that apply to it.
Sites / NetworksThe intended gateway, network, and connection configuration.
Firewall Rules / access policiesThe source user or team, destination, service, conditions, and matching decision.
Settings → IntegrationsThe configured identity provider and supported security integrations.
Settings → Administrators → Audit LogsWho changed an administrative setting and when.
Settings → Administrators → Roles & PermissionsWhich management tasks the administrator is allowed to perform.

Exact labels and available features can change by release and plan. Use the linked setup guide and your organization’s configuration record when following a specific screen path.

Work a “connected, but file share fails” ticket

  1. Record the customer, user, device, requested server name, service, error, and time. “Connected” is only one status.
  2. Confirm Timus Connect is signed in as the expected user and connected to the intended site.
  3. Inspect the matching user, team, device, and assigned profile in Manager.
  4. Check the relevant access or traffic event. Identify the actual denied condition or rule rather than assuming it is a password problem.
  5. Verify name resolution and the destination’s availability. Compare the case with a working user or device that should have the same access.
  6. If a change is required, apply it within the approved scope and retest the same resource. Document the rule, result, and any remaining server-side permission issue.

Read a denial usefully

For a fictional finance employee, a denial might involve the wrong team, an unmet device requirement, a destination excluded by policy, or a missing path to a site. Those require different corrections. Record the reason shown by the product. A successful connection to one application does not prove all destinations are allowed.

Keep management and user problems separate

An administrator lacking permission to edit a rule is different from an employee being denied access to a server. Check the administrator role for the first and the employee’s policy and traffic path for the second. If the client is not connecting, use the current Timus troubleshooting guidance and diagnostic logs before changing access policy.

PUT IT INTO WORDS

Check your understanding

An employee is connected in Timus Connect but cannot use one internal application. What details make the ticket actionable?

Show an example answer

Record the customer, signed-in user, device, site, application hostname, destination port, time, and error. Review the matching policy decision, team and profile, then check DNS and the destination service. Connection status alone does not show that this application is permitted.

File shares ↗

A file share lets other computers access a folder over the network. The network path finds the server and share; the user’s permissions decide what they can do there.
