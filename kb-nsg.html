Azure NSGs_

Tool guide Lab application

IN PLAIN ENGLISH

An Azure Network Security Group is a set of traffic-filtering rules attached to a subnet, a network interface, or both. It can allow or block a VM’s network traffic before that traffic reaches Windows.

Recognize the Azure resources

A virtual network is Azure’s network space for connected resources. A subnet is an address range within it. A VM’s network interface (NIC) attaches it to a subnet. Physical computers also have NICs and physical networks also have subnets; these ideas are not exclusive to Azure. The NSG is the Azure-specific resource.

Read a rule

FieldFictional example
DirectionInbound: traffic arriving at the associated resource.
Source10.20.10.0/24: where the connection originates.
DestinationThe intended server address or supported resource group.
Protocol and destination portTCP 3389: an RDP connection to the server.
ActionAllow or Deny.
PriorityA lower number is evaluated first. The first matching rule determines the NSG’s result.

“Source IP, source port, destination IP, destination port, protocol” is often called a five-tuple. In plain terms, it identifies the two ends of a particular kind of network conversation. You do not need to memorize the phrase to read the fields correctly.

Follow the path

Where both associations exist, new inbound traffic is checked by the subnet NSG and then the NIC NSG. Outbound traffic encounters them in the reverse order. All applicable controls on the route must allow the connection. An NSG allow rule cannot override a deny in another applicable NSG.

Inbound packet→Subnet NSG→NIC NSG→Windows Firewall→Application

Windows Firewall runs inside the VM’s operating system. It is another checkpoint. The application must also be running and listening on the required port. The diagram shows this simple inbound path; other deployments can place additional appliances or services along their routes.

Use the Azure views

  1. Find the VM’s networking configuration and identify its NIC, subnet, and associated NSGs.
  2. Open each relevant NSG and inspect inbound or outbound rules for the actual connection.
  3. Check effective security rules for the NIC rather than assuming one custom rule is the complete policy.
  4. Check routes and the guest operating system when the NSG result does not explain the symptom.
  5. Retest with a new connection after an approved change and record the exact source, destination, and result.

NSGs are stateful: return traffic for an allowed flow is handled using connection state. A changed rule should not be assumed to terminate every established connection immediately. NSGs can affect internet and internal traffic where their associations apply; they are not limited to communication between local VMs.

What the study lab demonstrated

The honeypot lab changed the Azure-side controls and Windows Firewall separately to expose the test machine. That showed two different enforcement locations. Its deliberately broad exposure is an experiment, not a configuration to copy onto a customer’s normal server.

PUT IT INTO WORDS

Check your understanding

An NSG permits RDP, but the VM still cannot be reached. What other checks matter?

Show an example answer

Check every applicable NSG, effective routes, the actual source and destination, Windows Firewall, and whether Remote Desktop is listening. Allowing traffic through one checkpoint does not make the whole path work. Use a new connection when verifying changed rules.
