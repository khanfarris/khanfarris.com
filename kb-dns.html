NOTE 06 / Networking

DNS_

Concept Scenario study

IN PLAIN ENGLISH

DNS translates names such as portal.example.com into information computers can use, often an IP address. It helps find a destination; it does not establish the connection.

Why names need a lookup

People remember a name more easily than a server’s IP address. When an application needs an address, your computer checks available cached information and normally asks its configured DNS resolver. The resolver may answer from its cache or ask other DNS servers until it finds the authoritative answer. Authoritative means the server holds the published records for that DNS zone.

Caching saves repeated lookups. A record’s TTL, or time to live, tells a cache how long it may keep that record before checking again. This helps explain why a DNS change can appear to work on one device while another still uses an older answer.

Records you will encounter

RecordWhat it tells you
A / AAAAThe IPv4 / IPv6 address associated with a name.
CNAMEAn alias pointing to another name.
MXWhich mail servers receive email for a domain.
TXTText used for purposes such as domain verification and email authentication policies.
PTRA reverse lookup from an IP address to a name, when configured.
SRVWhere a particular service can be found; Active Directory uses these to locate domain services.

Separate a name problem from a service problem

A user says websites fail, but your remote-support session still works. That proves some connectivity remains. It does not prove DNS is the cause: an existing session might not need a new lookup, and websites may use a different path or policy.

ipconfig /all
nslookup portal.example.com
Resolve-DnsName portal.example.com
Test-NetConnection portal.example.com -Port 443

These Windows checks show the configured DNS servers, query a name, and test the service’s TCP port. Replace the example with the actual affected hostname. Test-NetConnection proves a TCP connection can be established, not that HTTPS or the application is healthy. Browsing to a bare IP can fail because certificates and website routing expect a hostname.

Read the symptom before changing settings

SymptomUseful next check
Name does not exist / NXDOMAINCheck spelling and whether the expected record exists in the correct DNS zone.
Query times outCheck reachability to the configured resolver and whether it answers other queries.
An unexpected address is returnedCompare intended records, caches, split DNS, and recent changes.
Correct address, but application failsCheck the service port, TLS, proxy, firewall, and application health.

Internal names may only exist on company DNS servers, often reachable through an approved remote-access path. Replacing corporate DNS with a public resolver can break domain logons or file-server lookups. Record the query, resolver, answer, and time before clearing a cache; that evidence can explain what happened.

PUT IT INTO WORDS

Check your understanding

A name resolves to the expected IP, but the website still fails. What has DNS proved?

Show an example answer

It has provided the expected address for that lookup. It has not proved that the service port is reachable, the TLS handshake works, or the application is healthy. Test those separately and compare the scope of affected users.
