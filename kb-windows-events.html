NOTE 17 / Cloud & telemetry

Windows events_

Concept Lab application

IN PLAIN ENGLISH

Windows event logs record activity on a computer. Event IDs tell you what kind of event was recorded; the event’s fields explain who, where, when, and how.

Find the event at its source

Open Event Viewer on the intended Windows machine and inspect the relevant log. System includes operating-system and service events. Application contains application events. Security contains audited security activity. Which events appear depends on audit configuration, system role, activity, and log retention.

Filter by a sensible time range and event ID, then open the event’s details. Note the computer name and time zone. A log collector provides another copy or view of selected data; finding an event locally helps determine whether an apparent gap is a collection problem.

Three sign-in events to recognize

Event IDWhat it recordsWhat it does not prove
4624A successful logon on the computer recording it.That a person opened a desktop, or that the access was authorized.
4625A failed logon attempt.That an attacker succeeded or that every failure was malicious.
4672Sensitive privileges assigned to a new logon.A fresh privilege-escalation attack; legitimate administrative and system logons can generate it.

Read the logon type

A logon is not always someone typing into the Windows sign-in screen. Type 2 is interactive; type 3 is network, such as access to a shared resource; type 5 is a service; type 10 is RemoteInteractive, commonly RDP. There are additional types, so check the event reference for unfamiliar values.

A type 3 logon does not mean an RDP desktop session. Also, the “Subject” account can be the account reporting or requesting the operation. Read the relevant New Logon or Account For Which Logon Failed fields rather than treating every account field as the same identity.

Build a small timeline

Fictional example on SRV-01
10:01  4625  user: alex  source: 10.20.10.25
10:02  4625  user: alex  source: 10.20.10.25
10:03  4624  user: alex  logon type: 10  logon ID: 0x8F12
10:03  4672  subject: alex  logon ID: 0x8F12

This is a sequence worth checking, but two failed passwords followed by a legitimate admin logon is one possible explanation. Match the computer and Logon ID to associate relevant events within that host session, alongside timestamps and account details. Logon IDs are not a global identifier across every machine or reboot. Then inspect what the session did and whether the source and account use were expected.

Use the fields to avoid overclaiming

For failed logons, inspect the status and substatus, logon type, account, and source information. For successes, determine the session type and related activity. A missing or placeholder IP does not identify a remote source. Record “successful authentication observed” separately from “compromise confirmed.”

Local first, then collection

If Event Viewer contains a known event but the query platform does not, check collection rules, agent health, table, workspace, and time range. If neither contains it, check whether that event was generated and auditing was enabled.

PUT IT INTO WORDS

Check your understanding

A 4624 is followed by a 4672 with the same Logon ID on one host. Does that prove privilege escalation?

Show an example answer

No. It shows a successful logon and sensitive privileges assigned to that session. This can be normal for an administrative or system account. Check the account, logon type, source, time, expected role, and subsequent actions to decide whether the activity is suspicious.
