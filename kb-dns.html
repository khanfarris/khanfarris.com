NOTE 05 / Networking

DNS: names versus reachability_

Study basis: Scenario study

THE PRINCIPLE

Test name resolution separately from the ability to reach an IP address or service.

THE CONNECTION

An active remote-support session during a website outage proves some connectivity remains. It narrows the investigation without proving that every network dependency is healthy.

Follow the contradiction

DNS resolves names into records used to locate services, including IP addresses. A user opening a website by name depends on resolution before a new connection reaches the intended destination. A DNS failure can therefore resemble a broad internet outage.

An established remote-support session may continue while new name lookups fail. Existing connections or cached answers can explain the apparent contradiction. DNS is then worth testing early, while proxy policy, web filtering, and application-specific faults remain possible.

Separate the questions

  1. Scope: identify affected users, locations, names, and exact errors.
  2. Configuration: inspect the address, mask, gateway, and configured DNS servers.
  3. Resolution: query the failing name through the intended resolver.
  4. Connectivity: test the relevant address and service separately, accounting for filtering.
  5. Comparison: compare a working client and internal versus external names where relevant.
ipconfig /all
nslookup fileserver01.example.test
nslookup example.com

The file-server name is illustrative. Use the affected organization's names and approved DNS servers. A public resolver normally cannot resolve private corporate records and is not an automatic replacement for domain-client DNS configuration.

Interpret results precisely

An expected address returned by a query demonstrates that lookup succeeded at that moment. It does not establish application-port reachability, service health, or user authorization. A timeout and an authoritative answer that a name does not exist also call for different follow-up checks.

A failed ping does not prove a device is offline: ICMP may be filtered. Opening an HTTPS site directly by IP is not a clean substitute for a DNS test because certificate validation and virtual hosting depend on names. Test resolution and the required service independently.

The mapped-drive connection

A UNC path such as \\fileserver01\Accounts depends on name resolution, file-service connectivity, authentication, and authorization. DNS is one dependency in that chain. Correct the demonstrated failure, verify the original user task, and document which evidence distinguished it from other causes.

CLOSE THE NOTES. MAKE THE CONNECTION.

Recall check

Remote support works, but users report that websites fail. Is DNS definitely broken?

Reveal the reasoning

No. Existing connectivity is a clue. Query a failing name through the intended resolver and separately test the required service path, then compare scope and recent changes.
